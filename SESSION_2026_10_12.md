## Key Technical Decisions Made

### 1. `runCloudflareWorkersAI` is `public` on `GenerationPipeline`
Made public (not private) so the `Parameters<GenerationPipeline['runCloudflareWorkersAI']>` spread type works in the agent stub and so tests can call it directly via `Object.create(GenerationPipeline.prototype)`.

### 2. `this.ctx.env` via getter, not snapshot
The pipeline context includes:
```typescript
get env() { return self.env; }
```
This prevents stale env capture when tests replace `agent.env` after pipeline construction. Every `this.ctx.env` access in the pipeline reads the live value at call time.

### 3. `getKillSwitchStatus` and `getDisabledMsg` are closures inside `run()`
Both are defined fresh on every call to `run()`, closing over live `this.killSwitchCache`. They are not captured at `createToolHandlers` factory time. This ensures the kill-switch reads current state on every invocation, not a snapshot from when the generation started.

### 4. `createToolHandlers` called per generation
At `generation-pipeline.ts:797`, inside `run()`. Not a class field, not memoized. A new set of tool handlers is created for every generation request.

### 5. `pendingCompletenessRepair` survives hibernation via SQL
After the move, this field lives on `GenerationPipeline` (starts as `null` on every wake because `_pipeline` is re-created). Persistence uses the `pending_repair` D1 table. Both `noteRepairQueued` and `resolveCompletenessRepair` lazily restore from SQL when they find the in-memory field is `null`. Behavior is identical to commit e99257d — only the host object changed.

## Read-only Investigation: Route Coverage False Positives

### Finding
`extractWorkerRoutes` (`src/lib/api-coverage.ts:69`) only recognises chained-router syntax:
```
.<method>('/api/...', handler)
```

The baseline `worker/index.ts` template (`src/lib/workers-starter.ts:26-52`) uses `if/else` pathname dispatch:
```typescript
if (url.pathname === '/api/items' && request.method === 'GET') { ... }
if (url.pathname === '/api/items' && request.method === 'POST') { ... }
const match = url.pathname.match(/^\/api\/items\/([a-zA-Z0-9-]+)$/);
```

The repair prompt tells the model to "Follow the routing, database and auth patterns already present in that file" — directing it to write more if/else dispatch — which `extractWorkerRoutes` also cannot parse.

### `extractWorkerRoutes` — unrecognised syntaxes
1. `if (url.pathname === '/api/...')` — baseline template style
2. `url.pathname.match(/^\/api\/.../)` — regex routing (baseline parametric routes)
3. `switch (url.pathname) { case '/api/...': ... }` — switch dispatch
4. `app.route('/api/products', subRouter)` with relative sub-routes — Hono nested routing
5. Route path in a variable: `const P = '/api/foo'; app.get(P, ...)`
6. Dynamic template path: `` app.get(`/api/${entity}`, ...) ``

### `extractApiFetches` — unrecognised syntaxes
1. `fetch(url)` where `url` is a variable (not inline string/template)
2. `fetch('/api/' + variable)` — string concatenation
3. `` fetch(`${base}/api/products`) `` — dynamic prefix before `/api/`
4. `new Request('/api/...')` not wrapped in `fetch()`
5. Non-fetch HTTP: `axios.get(...)`, `ky.get(...)`, `useSWR(...)`, `$.ajax(...)`
6. Fetch calls outside `/src/` files (e.g. in `/worker/`)

### `checkApiRouteCoverage` reads only `worker/index.ts`
Confirmed at `generation-pipeline.ts:377`:
```typescript
const workerContent = allFiles.get('/worker/index.ts') ?? allFiles.get('worker/index.ts');
```
No other file under `worker/` is consulted.

### Status
**Not fixed in this session.** The mismatch between the baseline routing style and the regex in `extractWorkerRoutes` is a known gap. Any app generated from the baseline will produce false "missing route" warnings. Fix would require extending `extractWorkerRoutes` to also parse if/else pathname dispatch — deferred.
